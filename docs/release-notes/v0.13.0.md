# Pith v0.13.0 release notes

Released 2026-10-25. For Pith users: developers, pack authors, operators and the people supervising coding agents. The
maintainers' record of the same release is [the changelog](../../CHANGELOG.md) and
[RFC 0007](../rfc/0007-autonomous-assurance-and-runtime-composition.md).

Pith v0.13.0, merged on 2026-10-25, lets Pith check more of your system without a person in the loop: services composed from several packs, the adequacy of a pack itself, concurrency, live production behaviour and work done by agents in parallel. Every new check ships with a known-wrong example it must refuse for exactly the right reason, and none of the existing safety rules was relaxed.

## At a glance

Six capabilities, each aimed at a different moment in the life of a Pith-checked application.

| Capability | For | What you run | What it catches |
| --- | --- | --- | --- |
| Runtime composition | Developers wiring several packs into one service | `pith compose verify`, `pith compose stagger` | A multi-step operation that leaves components disagreeing after a crash or a lost reply; an upgrade of one component that damages another's data |
| Adversarial adequacy | Pack authors | `pith pack redteam` | Wrong implementations your pack's own checks would wrongly accept |
| Distilled counterexamples | Coding agents and the people supervising them | every run; `pith packet distill` | Nothing new: it rewrites failure reports so an agent can fix the cause without seeing the judge's code |
| Deterministic interleavings | Anyone with concurrent code | runs inside the existing checks | Race conditions, found on every run instead of once in a while |
| Shadow oracle | Operators running a service in production or staging | `gen/out/monitor.py shadow`, `pith trace harvest`, `pith trace replay` | A live service whose behaviour drifts from the contract after it was accepted |
| Fork-join handoffs | Teams running several agents in parallel | `pith handoff merge` | Two changes that each pass alone and break each other when merged |

## Composed systems, checked at runtime

You can now check a service built from several packs while it runs, with failures injected between the steps of an operation that spans them. Before this release, Pith checked compositions only as TLA+ models; the running services were judged one pack at a time.

How it works:

- A composition contract (`composition.yaml`) may add a `runtime` block naming one process per component and a test driver.
- `pith compose verify <composition> --candidate <app>` starts each component behind its own fault-injecting proxy. The driver crashes a process at the moment a call reaches another component, drops replies after the work was done, and severs retries.
- After each fault the components must settle on their own, without any client retrying. The shared rules are checked from each component's own records, never from what the coordinating service says about itself.
- `pith compose stagger` upgrades one component's data on a running composition and requires every other component's data to stay byte-identical.

The reference composition, `compositions/booking-quota`, books a room, then takes one unit of quota for it; if quota is refused, the booking is cancelled. Two rules must hold once nothing is in flight: active bookings and quota grants name the same requests, and the receipt a client gets matches both.

What it catches, shown with known-wrong versions:

- `split-saga-leak` forgets an operation it was in the middle of when it crashed, leaving a booking with no quota.
- `orphan-receipt-on-abort` tells the client "accepted" for a booking it later cancelled.
- `touches-quota-store` is an upgrade of the booking component that quietly rewrites the quota component's data.
- `drops-compensated` is an upgrade that deletes cancelled bookings, so old receipts no longer match.

The booking and quota components each still pass their own packs, so the composition check adds what no single pack can see.

## Find the gaps in your own pack

Pack authors can now ask Pith to find wrong implementations their pack would wrongly accept, and the pack cannot be released while a found gap stays open. The known-wrong examples an author writes by hand are only the ones the author already thought of.

1. Add a `redteam` section to `pack.yaml`: the reference example, the files mutants may change, and, for the model, how to ask whether a design is accepted.
2. Run `pith pack redteam <pack> --generate`. Pith makes small deterministic changes (a comparison flipped, a constant off by one, a lock removed) and judges each one exactly as it would judge a real candidate.
3. Bring outside mutants as saboteur packets (`gate/schemas/saboteur-packet.schema.json`): a wrong implementation plus a witness test, written by a colleague or an agent from your `INTENT.md`.
4. A mutant the gate accepts while its witness shows it breaks the intent is a confirmed gap. It is recorded in `redteam/gaps.yaml`, and `pith pack check --release` refuses the pack.
5. Tighten the checks, run again, then `pith pack redteam <pack> --promote`. The gap becomes a permanent known-wrong example with the exact refusal it now gets.

Generated mutants with no witness are reported as "unkilled": possible gaps or harmless changes, never counted as gaps. On the bundled demonstration pack, the gate killed 18 of 38 generated mutants before tightening and 23 of 38 after. A follow-up change in the same release fixed the same weakness in the `pith pack new` scaffold, so new packs start without it.

## Failures your coding agent can act on

Every judge run now also writes a second, redacted task packet (`TASK.distilled.md` and `task-packet.distilled.json`) that tells an agent what went wrong in the contract's own words, without showing it the judge. Use it when an agent works from the release alone and must not see the harness. The original `TASK.md` is unchanged.

What it removes:

- absolute file paths from the judging machine
- Python and Node.js stack traces
- the test harness's own source code and its code-style names, unless your pack's documents use the word

What it shows: the failing check, the contract records involved, and a counterexample as a short list of steps, with what was expected and what was observed. Where a pack provides an offline oracle, the steps are shrunk to the shortest sequence that still shows the problem. For the reservation pack's known receipt bug, the agent sees four steps (create an account, authorize, release, retry the release) ending in "expected released: true, replayed: true; observed released: false".

Run `pith packet distill <evidence>` to rebuild it for an earlier run. `experiments/harness.py feedback` hands it to an agent between repair attempts. Pack authors make their failures read this way by putting one `pith-counterexample` line in a test's failure message ([pack authoring guide](../PACK-AUTHORING.md)).

## Race conditions caught on every run

Concurrency bugs that used to show up only when thread timing happened to line up are now found on every run, with the same counterexample each time. The judge runs the concurrent requests one at a time and tries every ordering within a small bound (at most one or two forced switches), so a race inside that bound cannot slip through by luck.

| Known-wrong example | Pack | Orderings tried | Orderings that break it |
| --- | --- | --- | --- |
| `check-then-insert` (books an interval checked earlier) | booking | 30 | 6 |
| `unlocked` (no lock around the quota count) | quota | 40 | 6 |
| `split-decision` (new: decides outside its lock) | reservation | 10 | 4 |

The results were identical across five repeated runs, and the correct examples show no violation. The older timing-based test never caught `split-decision` in five runs.

The new checks run inside each pack's existing tests for Python services and libraries; nothing extra to invoke. Node.js candidates run single-threaded JavaScript, and the checks skip them and say why.

New storage option for the reservation pack: `profile: sqlite-occ`. It decides without holding the database write lock and commits only if the account has not changed since it was read, retrying up to 100 times. Its tests check every explored ordering of two and three concurrent operations against some one-at-a-time order of the verified core, and three deliberately broken variants are caught every time. `examples/build-occ` is a full application on it.

## A shadow oracle beside your live service

Operators can now run Pith's monitor next to a service in staging or production and be told when its behaviour stops matching the contract. A drift found this way becomes a permanent regression test. Until now the monitor and the verified core ran only while the gate judged an application.

1. Start the sidecar: `python3 gen/out/monitor.py shadow --events <service URL>/events --out divergences.log`. It is a separate process that reads the service's event feed, so it cannot slow or crash the service. It replays every committed operation through the pack's oracle, which decides with the verified core.
2. When the live answer differs from what the contract requires, it writes one divergence record.
3. `pith trace harvest divergences.log --out <dir>` shrinks the logged operations to the few that matter. It writes the trace, a Dafny test of it for the pack's trace suite, an unsigned provenance note and a draft revocation.
4. `pith trace replay <dir>/trace.yaml --candidate <app>` runs the trace against an application to show whether it fails.

In the bundled demonstration, a copy of the club desk carried a drift that only appears once an account holds three live holds. The sidecar caught it at the 16th operation; harvest cut 15 operations to 6. The Dafny test passed against the verified core, and replay failed on the drifted desk and passed on the accepted one.

The revocation stays a draft on purpose. It applies only if the deployment was the exact artifact Pith accepted (`pith deploy check`); otherwise the deployment ran something the evidence never covered, and nothing is revoked. Services can also attach the shadow in-process (`Shadow.attach`): it never raises into the host and counts what it drops instead of blocking.

## Merging parallel agents' work

You can now give several agents the same accepted application, let each change a different part at the same time, and merge the results in one step. Pith re-checks the merged application and reuses only the proofs and model checks the changes could not have touched. Handoffs used to be one agent after another.

- A pack declares partitions of the application in `pack.yaml`. The reservation pack has design, integration (service, adapter, manifest), presentation (UI), migration and a generated interface no branch may change.
- `pith handoff merge --base-candidate <base> --base <base evidence> --branch a=<dir>:<evidence> --branch b=<dir>:<evidence> --out <merged> --judge <new evidence>` refuses two branches touching the same partition or the same file. It writes the merged application and judges it, offering every branch's earlier evidence for reuse.
- `--reuse` can now be given several times on any judge run. A result is reused from whichever earlier run matches it exactly.

What is never skipped: every check that starts your service, browser workflows included, runs again on the merged application. That is deliberate, and it is what catches the hard case. In the recorded example (`evolution/handoff/fork-join`), one agent redesigns the page to read its input limits from the service's `/openapi.yaml`, and another trims that "unused" route from the service. Each change is accepted on its own and they touch different partitions, yet the merged page cannot load and the merge is refused. A merge of the page redesign with a storage-profile swap is accepted, reusing exactly the 10 cached results (the kernel proof and every model check).

## Upgrading to v0.13.0

No stored data needs migrating, but every application must be judged again under the new releases, and some previously accepted ones may now be refused.

| Pack | Version | What changed for you |
| --- | --- | --- |
| reservation | 0.12.0 → 0.13.0 | New deterministic race test in the lifecycle harness; new `sqlite-occ` profile choice; shadow mode in the generated monitor (regenerate `gen/out/` with `obligations/boundary/generate.py`); partitions for merges |
| booking | 0.12.0 → 0.13.0 | New deterministic race test (Python services) |
| quota | 0.2.0 → 0.3.0 | New deterministic race test (Python libraries) |
| approval, tally demos | unchanged versions | Resealed only, because the evaluator changed |

- Stricter checks: a Python application that was accepted with a latent race can now be refused at its lifecycle check. The fix is in your code, not the check.
- Re-judge: every release digest changed, and evidence never carries across releases, so a run with `--reuse` on old evidence reuses nothing.
- Regenerate: reservation candidates must refresh `gen/out/monitor.py`, or the "generated artifacts current" check refuses them.
- Unchanged: no contract version changed, so no migration is needed. The reservation pack's Atomicity record was reworded to cover both storage profiles; its obligation and version are the same.
- All file formats are additive: new optional fields and new format names, nothing renamed or removed ([COMPATIBILITY.md](../../COMPATIBILITY.md)).

## Known limits

Each capability checks what it injects or explores; none of them proves an application correct.

- Runtime composition tests the faults it injects, not every possible crash point; each component's own atomicity is still its pack's job.
- A closed red-team gap means the gate now refuses that wrong implementation, not that the pack is complete. A gap is only as meaningful as its witness, which a person still has to judge.
- The race checks explore orderings within their bound and only the requests a test sends. They cover Python services and libraries; a store whose race involves no lock, sleep or database statement is reported inconclusive rather than passed.
- The shadow oracle sees only what the service records in its event feed; a side effect that bypasses the feed is invisible to it.
- Disjoint partitions say which evidence carries over, never that the merged application works; only the re-run checks show that. Conflicts are detected per file, not per line.
- The redaction in distilled packets is a filter tested on every fixture in the project, not a proof that nothing can leak.
- No AI model runs in CI. The saboteur packets and the fork-join branches are scripted demonstrations, not measurements of agent behaviour.
- Every pack stays at `draft`: no one other than the maintainer has reviewed this release, as [GOVERNANCE.md](../../GOVERNANCE.md) requires before a pack is called released.

## How it was built and verified

The release was designed first as RFC 0007 and built one capability at a time; each had to pass the whole suite before the next began. The work was done in a single Claude Code session, with parts delegated to sub-agents whose results were reviewed and re-run.

- Baseline: the unmodified v0.12.0 code passed all 26 CI steps on macOS and in a Linux container before anything changed.
- Final run: 34 of 34 steps passed on macOS and in a native arm64 Linux container. That is every CI job except the x86 isolation container, the contract upgrades of all four packs, and all 21 cases of the mutation matrix. macOS needed two local-only workarounds for platform differences; Linux needed none.
- Each new evaluator piece had to pass the check that the evaluator stays free of any pack's vocabulary. That check caught three slips ("sqlite", "ledger", "service/run.py"), and each was fixed by having the pack declare the value instead.
- On GitHub, both pull requests passed all 16 CI checks, including the isolation container job, before they were merged: #8 (the release) and #9 (the scaffold fix).
- Two intermittent failures that predate this release are recorded in the validation record: model-checker runs started in parallel sometimes collide, and one booking profile test can fail when re-run in the same workspace.
