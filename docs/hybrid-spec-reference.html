Hybrid spec-driven development

An assurance-oriented extension to spec-driven development: validated behavioral obligations, scoped verification evidence, and change control that keeps the evidence current.

Spec-driven development with one change: the spec has two layers, and only one of them supports correctness claims. Prose carries intent and rationale. Formal properties, with their meaning validated and their semantics pinned, carry what must hold. Code is checked against the properties and reviewed against the prose.

No unvalidated interpretation of prose is the sole basis of an automated correctness claim.

  • Every claim names its approved behavioral obligation and the evidence behind it, with the evidence's scope: what was checked, over what inputs or states, under which assumptions.
  • In particular: a test the implementing model derived from its own reading of the prose is not approved evidence. A reviewed, approved acceptance example is, as a point property.
  • Editorial prose changes change nothing. A change to intended behavior reopens intent validation until the formal layer is reconciled; it does not by itself invalidate proofs.

What changes in the loop

Current practice is not prose-only: some spec-driven tools, Kiro for example, already extract properties from EARS requirements, run property-based tests, and are careful to call the result evidence rather than proof. The hybrid's contribution is narrower and firmer: properties with pinned semantics and validated meaning, bound to a state model, with evidence that stays scoped and current.

StepCurrent practiceHybrid
SpecifyStructured prose with acceptance criteria; properties extracted from it by the tool.Same prose, plus a property per requirement over a named state model, with timing semantics and atoms pinned and the meaning validated by trace review, or an explicit informal opt-out.

ImplementLLM derives code from the spec.Unchanged. Tests assert properties by id. Critical cores are written in a verifiable language and transpiled.

ChangeEdit the spec, regenerate.Classify the edit. Editorial: nothing moves. Intent: validation reopens. Property, atom, model, build, or schema: the dependent evidence goes stale. Then regenerate.

The spec stays the source of truth. Prose is the truth about intent; properties record the approved obligations for required behavior. Code is still regenerated from the spec; the regeneration is checked against the second and reviewed against the first.

2

One requirement, end to end

Payment authorization: one account, concurrent authorization requests, a limit that in-flight reservations count against. The requirement is REQ-AUTH-001; its record is in section 3. Available limit is the only authorization criterion modeled; the requests are otherwise eligible.

Illustrative example.

The model fragments, record, identifiers, and verification outcomes below demonstrate the proposed workflow. They are not reported results from an executed implementation or deployment. Where a counterexample is described, it is one the reader can construct by hand.

2.1

Sentence

prose · spec/requirements

When an authorization request exceeds the account's available limit, the system shall decline the request and shall not reserve funds.

Five things are open, and all five matter under concurrency. Each becomes a recorded decision.

2.2

Decisions

Open in the proseDecisionWhy
When is "exceeds" evaluated?At the decision step, the linearization point of Decide(r). Not at receipt.Under a receipt-time policy, two requests of 60 that each observe 100 available at receipt both authorize, leaving 120 reserved against a limit of 100: INV1 fails. Evaluating availability atomically at the decision step removes that trace. The counterexample is about this policy and this model, not every receipt-time design.
What does "when" mean?Immediate: the response holds in the post-state of the same atomic step. Not next, not eventually, not within a bound.Receipt-to-decision latency is a separate liveness requirement, REQ-AUTH-002.
Must the trigger persist?Single-shot. Evaluated once per request; a retry is a new request.Re-evaluation would couple this requirement to idempotency (REQ-AUTH-007).
"Exceeds" and "available"Strict: amount > available, where available is limit minus posted minus live reservations, read in the same step. Equality authorizes, and that is its own property (P0), not an inference from P1's silence.An implication says nothing when its antecedent is false. Without P0, "always decline" satisfies every property here.
"Shall not reserve"A reservation exists only while its request is Authorized (P2); the account never exceeds its limit (INV1); Declined is terminal (P3)."No reservation while Declined" would admit reserve-then-release-then-decline. P2 as stated forbids a reservation in any other status, so the optimistic-reserve bug is out.

Trace review asks whether the properties mean what stakeholders meant. Wrong candidates ask whether the properties reject what stakeholders consider wrong. Both are required before the formal layer may serve as an oracle.

The ladder

Evidence should match the failure mode, consequence, and observability of the requirement, not a fixed inventory of tools. The table is the default assignment; the principle governs exceptions, which are recorded with their reasoning. Rungs are cumulative by default.

RungBindingsWhat a pass supportsDefault for
1Prose spec, derived code, review, example tests, tool-extracted property tests with unvalidated meaning.no correctness claim The obligation was never approved.Nothing with consequential behavior.
2Validated properties executed by stateful property-based tests; a live monitor where the behavior is observable in production.Not falsified over executed runs; no violation observed in the window.Stated behavior with bounded consequence: contracts, schemas, audit events. A pure library skips the monitor.
3Plus a model-checked state model.Properties hold throughout the configured finite model.Concurrency, protocols, state machines, retry and idempotency.
4Plus a proven core with the properties as contracts, transpiled and pinned.Postconditions hold for all contract-satisfying inputs, under stated assumptions.Money-moving and safety invariants.

A requirement moves up when its monitor fires, when it is named in an incident, when its blast radius grows, or when a counterexample appears after its gate was satisfied. It moves down only with an explicit risk reassessment: a redesign that removes the concurrency or the external dependency can legitimately remove the binding that existed for it. Requirements that resist formal oracles (copy, layout, interaction quality) keep human evaluation and an informal marker; absence of a formal oracle does not mean absence of evaluation.

How the layers can agree and still be wrong

FailureIn this exampleCaught by
Spec driftA hotfix in the wrapper reads available balance from a 500 ms cache. Prose and properties still say "same step." With nothing tracking the build, the gate would still read satisfied.The dependency set marks stack-level claims stale on the build change, before any binding runs. When they run, burst PBT can surface the stale read and the monitor's cross-check fires on divergence; neither is guaranteed within a finite run. The pinned Dafny core is unchanged, which is correct: the proof's claim never covered the wrapper.
Formalization ≠ intentThe formalizer uses the wrong boundary consistently: P0 authorizes only when amount < available, P1 declines when amount ≥ available. The implementation satisfies both mistaken properties; every checker passes; customers at exactly their limit are declined.Boundary traces in the review set, signed against the traces rather than the formula, and the "decline at equality" candidate, which approved intent requires the set to reject. Verification succeeded against an internally consistent, wrong formalization; only validation sees it.
Inadequate property setP0 is missing. An implementation that declines everything satisfies P1, P2, P3 and INV1 and every checker passes.Wrong-candidate implementations run against the property set before it is accepted as an oracle: always-decline, decline-at-equality, optimistic-reserve, receipt-time availability. Each must be rejected by a named property.
Vacuous propertyAn atom binds to an unreachable predicate; P1's antecedent is never true; TLC and PBT pass trivially.Antecedent coverage: TLC asserts the trigger is reachable; Hypothesis records antecedent hits against a floor; Dafny carries a witness for the precondition; the monitor alerts on zero antecedents over a window with traffic.

6

Starting

  1. Pilot the whole method on one bounded workflow with consequential state transitions. Measure defects caught, but also how often trace review and wrong candidates change a property before code exists, whether bindings stay aligned, and what the evidence costs to maintain. Let those numbers govern rollout.
  2. In the pilot, add semantics, atoms, properties, verification (with covers and claim per binding), validation, and evidence_depends_on to each requirement record, with informal as the explicit opt-out. Replace any hand-typed status with a computed gate.
  3. Give the design artifact a state model with named variables and actions, and state the environment assumptions the requirements rely on.
  4. Before a property set becomes an oracle: trace review with boundary cases, and a short list of deliberately wrong candidates that the set must reject.
  5. Change the test-generation instruction: assert declared property components, stateful where there is state, with an antecedent-hit floor in CI.
  6. Generate monitors from the records where behavior is observable; make "monitor live" a release gate at the rungs that require one; let CI write results and claims.
The worked example, including every verification outcome in it, is illustrative, as noted in section 2. The TLA+ excerpt assumes a Reserved(a) sum helper and the full Decide action. Revised after external review: the property set gained P0 and a stronger P2, bindings now declare coverage and claim, and the single verified label was replaced by a gate over scoped claims.
